# LLM Science Exam — interview-grade RAG project

## Context

**Why this project.** You want an artifact that proves AI-Engineering skill in a technical interview. The Kaggle "LLM Science Exam" competition (Jul–Oct 2023, 2,600+ teams, closed) is an unusually good vehicle because its central finding is a *judgment* result, not a trick: closed-book classification plateaus around 0.70 MAP@3, while retrieval-augmented pipelines reach 0.90+. The 4th-place team reached top-5 with a **435M-parameter encoder** while 3rd and 5th needed 70B models to do marginally better. That is a story about information access beating parameter count, and it is exactly the kind of reasoning an interviewer is probing for.

**What you decided.** Kaggle-first compute (local 8 GB RTX 5050 for glue and fast iteration). Depth you can defend over raw score — a 0.89 you fully own beats a 0.92 you inherited. Plus a breadth layer showing you know what the 2026 stack looks like, not just what won in 2023. You have a Kaggle account but no API token yet.

**Time.** You have a few days. So this plan has two tracks: a **4-day core** that produces the complete defensible artifact, and an **extended track** of independent workstreams you can parallelize if you find more time or more machines.

**The framing that makes it work.** This is not a rank-chasing project — the competition is closed, late submissions earn no medal, and the leaderboard is private to you. Frame it as: *a reproduction study of the retrieval-vs-scale question under hard offline constraints, with the retrieval component measured independently of the reader.* Under that framing the 200-row training set stops being an embarrassment and becomes a forcing function for honest statistics.

**The one decision that shapes everything:** the 200 official `train.csv` rows are your **held-out gold test set**. You never train on them. All training data comes from public synthetic sets. One sentence to defend, and it is what makes every number in your README trustworthy.

## Competition facts (verified)

| | |
|---|---|
| Task | 5-option (A–E) multiple-choice science questions, exactly one correct. Generated by GPT-3.5 from Wikipedia STEM articles. |
| Metric | **MAP@3** — predict up to 3 ranked labels per id, space-delimited in a `prediction` column. Not MAP@5; the widely-cited Hippocampus's Garden writeup has this wrong. |
| Data | `train.csv` = **200** labeled rows (`prompt, A, B, C, D, E, answer`); hidden test ≈ 4,000 rows. |
| Rules | Code Competition — notebook-only submission, **internet disabled at runtime**, 9-hour limit. All external data/models attached as Kaggle Datasets. |
| Random baseline | **0.3667**, not 0.2. `(1 + 1/2 + 1/3) / 5`. Most people get this wrong; stating it correctly reframes every absolute score. |

**Metric consequences to state out loud:** always emit exactly 3 labels, never duplicates (extra guesses are free, so fewer than 3 is strictly dominated). Rank-1→rank-2 is worth 0.5 but rank-2→rank-3 only 0.167, so ranking effort belongs at the top of the list. Monotone rescaling of a *single* model's scores is a no-op for MAP@3 — calibration only matters for ensembling and confidence cascades.

## Extended track — independent workstreams if more time or resources appear

Each of these is designed to be **developed in isolation and merged late**. The interface contract is what makes that work: every retrieval leg writes `(question_id, chunk_id, rank, score)` parquet, and every reader leg writes `(question_id, option, prob)` parquet. Any leg can then be fused (RRF for rankings, rank-average or probability-average for readers) without touching another leg's code. Define these two schemas on Day 1 even if you only ever have one leg — it costs ten minutes and it is what makes parallelization possible at all.

| Workstream | Depends on | Payoff |
|---|---|---|
| **A. Learned-sparse leg** — `opensearch-neural-sparse-encoding-doc-v3-gte` | corpus shards only | +11 nDCG over BM25 at zero query-time GPU cost. The most under-appreciated upgrade available. |
| **B. Second corpus** — `jjinho/wikipedia-20230701` | corpus code | 1st place's main retrieval trick was *multiple different dumps*. Corpus diversity is cheaper than model diversity. |
| **C. Late chunking / contextual embeddings** | an 8k-context embedder | +9.0 nDCG on ConTEB for zero extra storage; ⚠ `pplx-embed-context-v1` would make the writeup genuinely stand out. |
| **D. LLM reader leg** — QLoRA on a 4–8B base model, per-option binary objective with prefix-KV-cache reuse | reader interface | The *expected* finding is the interesting one: a 435M encoder ties or beats it at ~15× lower cost. One honest row saying so is worth more than the score. |
| **E. Modern encoder reader** — ModernBERT-class, native long context vs DeBERTa's relative-attention extrapolation | reader interface | Directly tests whether the 2023 winner's cleverest trick has been obsoleted by architecture. ⚠ unverified — see Open Items. |
| **F. Ensemble + confidence cascade** | ≥2 reader legs | Route only the low-margin questions to the expensive leg; report the **accuracy-vs-cost Pareto curve**. The most production-flavoured artifact in the project. |
| **G. Reasoning retriever** — ⚠ `Alibaba-NLP/LaSER-Qwen3-0.6B` (MIT) | retrieval interface | Tests whether BRIGHT-style reasoning-retrieval gains transfer to science MCQ. Expect muted gains — and *that* is a publishable-quality negative result for your writeup. |

Workstreams A, B, C, G are retrieval-side and can run entirely in parallel with D, E which are reader-side. On one machine the binding constraint is the Kaggle GPU quota, so bias toward A and B (CPU-heavy) before D and E.

### What the LLM API budget buys (your stated extra resource)

Ranked by value, and note that **none of it is on the critical path** — the core 4 days need no API at all:

## The validation design (the intellectual core — do not compress this)

This is the section that separates you from every other candidate with this competition on their résumé, because almost nobody does it and every senior interviewer cares.

### The noise arithmetic

Per-row AP@3 is a 4-valued variable in {1, 0.5, 0.333, 0}. At a realistic operating point (top-1 ≈ 0.80) the per-row SD is ≈ **0.29–0.32**. So:

| n | 95% CI half-width |
|---|---|
| 200 (official gold) | **±0.040** |
| 1,000–1,500 (synthetic dev) | ±0.018 |
| 4,000 (full private test) | ±0.009 |

**A 200-row eval set cannot resolve anything smaller than a 4-point MAP@3 change.** Even the full private LB has ±0.009. That arithmetic *is* the explanation for why public-LB tuning destroyed people in this competition: the 0.01–0.02 swings competitors chased were sampling noise. Compute these from your own score vector rather than reciting them.

### Three tiers with different jobs

- **T1 — dev/selection.** ~1,500 held-out synthetic rows. Every design decision is made here. Use freely.
- **T2 — gold/confirmation.** The 200 official rows. **Sacred.** Hard cap of ~8 evaluations for the whole project, each logged with a date and a reason. Always reported with a 95% bootstrap CI.
- **T3 — out-of-distribution.** ~500 ARC-Challenge + ~500 MMLU-STEM. These are *human-written*, so they catch the one shift no amount of synthetic data can fake. (4-option — your MC head handles variable option counts natively.)

T3 buys the best sentence available: *"My synthetic dev said +3 points. My human-written holdout said +0.5. I didn't ship it."*

### Paired bootstrap, always

Unpaired CIs are the wrong test for "is B better than A." Two similar configs agree on ~90%+ of rows, so the SD of the per-row *difference* is far smaller. Run both variants on the same frozen set, compute per-row AP for each, and report a **paired bootstrap 95% CI on the difference** (10,000 resamples). Accept a change only if the CI excludes 0. This buys roughly a 5× resolution improvement for free. Ship an `mde()` helper that reports what effect size your eval set can actually detect at the observed disagreement rate.

Honest limit to state: if a change flips only ~15% of rows, the SE of the delta is still ~0.019, so small tweaks remain unresolvable. Say so rather than claiming them.

### Two leakage checks nobody does

1. **Article-level, not row-level, splitting.** Synthetic rows generated from the same Wikipedia article must not straddle the train/eval boundary — otherwise your *retriever* saw the eval question's gold article during reader training and the whole open-book measurement is contaminated. Enforce with `GroupKFold` on article id in `tests/test_no_leakage.py`.
2. **Contamination audit against the gold 200.** The public synthetic sets and the official 200 were both generated from Wikipedia STEM articles. The leak is not duplicate question text, it is a **shared source article**. Retrieve the top-1 article for each of the 200, intersect with your training set's source articles, report the count, remove the overlap, re-report T2. Also MinHash-dedupe question text (Jaccard > 0.8) across pools, because the `cdeotte` sets partly derive from `radek1`'s.

Finding and quantifying an article-level leak is a genuinely senior move.

### Best-of-N optimism

If you pick the best of N configs on a set with SE σ, the winner is optimistically biased by ≈ σ·E[max of N standard normals]. N=20 on T2 (σ=0.023) → **~0.04 of pure optimism**. That arithmetic is your justification for selecting on T1 and only confirming on T2. Report the number of configs you evaluated.

### Reporting rules

- No naked numbers. Every MAP@3 gets a 95% bootstrap CI.
- `experiments/log.csv`: config hash, git SHA, T1, T2 (only if spent), T3, CI, date, one-line hypothesis, verdict.
- **Explicitly mark any gain inside the noise band as "not resolved by my eval."** Volunteering that about your own result is the single most credible thing you can do.
- Hand-check the 200 gold rows and report how many labels you disagree with — that is your ceiling. If it's 5, the ceiling is ~0.97, not 1.0.

## Measuring retrieval independently of the reader (the centerpiece)

No forked notebook contains this. It separates the two failure modes and answers "where should the next week of compute go?" with a number instead of an opinion.

### Two proxies that bracket the truth

**Proxy A — source-article recall (lower bound).** Synthetic rows carry their generating article. Gold = that article id. Report **recall@{1,5,10,20,50,100}**, MRR@10, nDCG@10, with bootstrap CIs. It is a *lower* bound because Wikipedia is redundant — a different retrieved article may fully support the answer and still count as a miss. **Quantify that:** hand-inspect 30 "misses" and report what fraction were actually sufficient (expect 20–30%).

**Proxy B — answer-support recall (upper-ish bound, and it works on the gold 200, which have no gold passage).** A chunk counts as a hit if it contains the rare content tokens of the correct option, or scores above a cross-encoder threshold against `question + correct option`. This is the DPR paper's answer-string recall protocol. It is an *upper* bound because a chunk can contain the answer string without supporting the inference — hand-label 50 pairs to estimate the false-positive rate.

Then say: *"True support recall@5 is bracketed between 0.71 and 0.86."* Bracketing the unmeasurable and saying so is more impressive than one confident number.

### The attribution table — the money table

Hold the reader fixed, vary only what context it sees:

| Reader input | MAP@3 | Interpretation |
|---|---|---|
| No context (closed book) | ~0.65–0.70 | parametric-knowledge floor |
| Retrieved k=1 / 3 / 5 / 10 | | operating point + distraction onset |
| **Gold source snippet (oracle)** | ~0.93–0.95 | **reader ceiling with perfect retrieval** |

- `oracle − pipeline` = **retrieval-attributable loss**
- `1 − oracle` = **reader-attributable loss** (minus label noise)

This is what lets you say "a 70B model cannot recover more than N points, but fixing retrieval can recover M" and be *right*.

### The 2×2 failure decomposition (on the gold 200)

|  | reader correct | reader wrong |
|---|---|---|
| gold passage retrieved | working as designed | **reader failure** — distractor confusion, context too long, positional |
| gold passage missing | lucky / parametric | **retrieval failure** — where the budget goes |

Print counts and percentages; hand-annotate three examples from each failure cell.

### Two cheap, rare probes

- **Options-only bias probe.** Feed the reader *only the five options* — no question, no context. If MAP@3 ≫ 0.3667, the benchmark has a lexical shortcut (GPT-3.5 correct answers are often longer or more hedged than distractors) and part of your closed-book score is artifact, not knowledge. Quantifying your own benchmark's shortcuts is a strong senior signal.
- **Position sensitivity.** Inject the gold passage at position 1 vs last vs buried among 4 distractors → your own "lost in the middle" measurement.

### The plot that ties it together

Scatter **recall@5 (x) vs MAP@3 (y)** across all pipeline configs, annotate Spearman ρ. If ρ ≈ 0.9 you have *demonstrated on your own data* that retrieval dominates — the competition's headline finding, arrived at by your own measurement rather than by citation.

## Architecture

```
question + 5 options
  → query construction (prompt+all options | per-option queries)
  → STAGE 1: sparse retrieval over 270k ARTICLES
  → STAGE 2: dense + sparse over the ~5k chunks of the top-N articles
  → RRF fusion (k=60)
  → cross-encoder rerank 50→5
  → dedupe + neighbour-expand + assemble ≤1280 tokens
  → encoder reader, AutoModelForMultipleChoice, (bs, 5, L) → 5 logits
  → top-3 labels
```

**The key architectural decision: hierarchical article→chunk retrieval.** Stage 1 over 270k articles, stage 2 over only the ~2–5k chunks belonging to the top-N. This single choice eliminates the global index over ~20M chunks — which 15 GiB RAM physically cannot hold (20M × 384-d × fp16 = 15.4 GB of raw vectors before any index structure). Stage-2 dense search over 5k vectors is a plain `torch.matmul`: exact, GPU-resident, sub-millisecond, no index build, no FAISS to package offline. You traded a little stage-1 recall for the elimination of an entire infrastructure class — then you *measure* the stage-1 recall to prove the trade was cheap.

### Chunking

Sentence-split with **blingfire** (10–50× faster than nltk punkt). **3-sentence windows, stride 1**, capped ~200 words (the 2nd-place recipe). **Prepend `title + ": "` to every chunk** — 1st place's trick, and it matters more than it looks, because questions often reference the article topic only implicitly. Keep two granularities: paragraph-level for recall, sentence-window for precision/reranking. Stream with `pyarrow.parquet.ParquetFile.iter_batches()` and write shards; **never `pd.concat` the corpus** — that is the #1 way to OOM 15 GiB.

### Query construction matters as much as the index

Three variants worth an ablation each:
1. `prompt` alone
2. `prompt + " " + A + B + C + D + E` — usually the best single query; the options are free query expansion carrying the rare anchor terms
3. **5 per-option queries**, union the results. This is the retrieval side of 1st place's per-option contextualization: distractors often live in *different* articles than the gold answer, so a pooled query systematically under-retrieves the evidence needed to *reject* options.

### Reader

`AutoModelForMultipleChoice`. Input per option: `[CLS] context [SEP] prompt + " " + option [SEP]`, batched `(batch, 5, L)`. Forward flattens to `(bs*5, L)`, encodes, applies **one shared `Linear(hidden, 1)`**, reshapes to `(bs, 5)`, `CrossEntropyLoss` against the correct index. It is *not* a 5-output head. Consequences worth knowing: permutation-equivariant, so no A/B/C/D/E letter bias (unlike a decoder LLM reading lettered options); generalizes to variable option counts; but it **cannot** do cross-option elimination reasoning, and it costs 5 forward passes.

Two gotchas that silently cap you:
- `truncation="only_first"` so long context is cut, never the answer option.
- Retrieve training contexts with the **same retriever you use at test time.** Training on cleaner context than you get at inference is the most common RAG training bug and produces a reader that over-trusts its context.

**Why sequence length is the highest-ROI knob, mechanistically.** 4th place's score rose monotonically 512→1280 tokens. `microsoft/deberta-v3-large`'s config has `max_position_embeddings: 512` but also `position_biased_input: false` and `relative_attention: true, position_buckets: 256` — meaning it **never adds absolute position embeddings**; position enters only through log-bucketed relative attention. So the 512 is effectively vestigial and you can set `max_length=1280` with no model surgery. That is the crispest single technical insight in the project — put it in the README, and *measure* the extrapolation (train@1024/eval@1024 vs train@1024/eval@1280) rather than assuming it.

### Objective: multi-class vs per-option binary

Multi-class softmax over 5 (2nd/4th place, and what `AutoModelForMultipleChoice` gives you) is better calibrated and matches the metric natively. 1st place used per-option **binary** — and the real reason is not the loss shape, it is that binary permits **option-specific retrieval** and prefix-KV-cache reuse across options. Most summaries miss that. Decision: multi-class for the encoder; per-option binary only if you do the optional LLM leg. Report the tradeoff as measured, not cited.

## The 2026 stack — what a 2023 solution would get wrong

The 1st-place team picked their embedders off the MTEB leaderboard *as it stood in 2023*. Three years later almost every one of those choices is dominated. This section is the "breadth" layer you asked for: it is what makes the writeup read as current rather than as a museum piece, and it gives you a genuinely interesting slide — *"here is what I would change if this competition ran today."*

**Sourcing caveat, stated honestly:** the items below were verified against primary model cards and PyPI by a research pass on 2026-07-27. Anything marked ⚠ is explicitly unverified. **Two research passes did not complete** (see Open Items) — the reader/LLM landscape and the Kaggle platform facts are therefore *not* independently verified, and the plan routes around that by gating them behind day-1 checks.

### Four facts that invalidate 2023-era assumptions

1. **Dense retrieval now clearly beats BM25 zero-shot.** The BEIR-era folklore ("BM25 wins out-of-domain") is dead for general web/wiki text: BM25 sits at nDCG@10 ≈ 43 while 149M-param 2026 models reach ≈ 56. Hybrid still pays, but the gain is now ~2–5%, not the deciding factor. **Do not repeat the 2021 finding as though it were current** — that is a trap an interviewer may well set.
2. **Learned sparse beats BM25 outright, and its queries are free.** `opensearch-project/opensearch-neural-sparse-encoding-doc-v3-gte` (133M, Apache-2.0) scores BEIR ≈ 0.546 vs BM25's 0.434, and is **inference-free at query time** — queries are tokenizer + IDF lookup only, so it adds *zero* GPU latency at submission. Doc-side encoding is a one-time offline cost. This is the most under-appreciated upgrade available to this project.
3. **`transformers` is now 5.x** (5.14.1) and `sentence-transformers` 5.6.1. Any 2023 notebook code, and anything needing `trust_remote_code=True`, must be smoke-tested against v5 before you commit to it.
4. **You do not need an ANN index.** 4M chunks × 768-d in fp16 = **6.1 GB** — fits in a single T4's VRAM. A full 4,000-query × 4M-doc exact scan is ~1–2 seconds of GEMM. **ANN buys you nothing but recall loss and build time.** Use `faiss.IndexFlatIP`, or a plain chunked `torch.matmul`, and drop the dependency entirely. Stating this arithmetic out loud is a better answer than any HNSW tuning story.

### The Turing landmine that would waste a day

**Gemma-3-derived embedders produce garbage in fp16** — activations exceed fp16's 65504 ceiling. This hits `google/embeddinggemma-300m` and `microsoft/harrier-oss-v1-*`, which are otherwise the most attractive new small models. The `transformers` fix is still an **open PR**. On T4 you must run them in fp32 or not at all. Separately, `Qwen/Qwen3-Embedding-8B` emits **NaN embeddings in fp16** (0.6B and 4B are unaffected).

This is worth a line in the README: *"I chose a ModernBERT-backbone embedder partly because the best-scoring alternatives are numerically unsafe on the only GPU the competition allows."* That is a hardware-aware model-selection argument, which is rarer and more valuable than a leaderboard citation.

**Why the obvious alternatives lost:** `gte-modernbert-base` — same size and backbone, 1 point worse, and the worst decontamination delta in the study (its BEIR score is partly memorization). `snowflake-arctic-embed-*-v2.0` — Dec 2024, now beaten by models 2–4× smaller; no v3 exists. `BAAI/bge-m3` — Jan 2024; BAAI has shipped no new general English embedder since mid-2025. `nomic-embed-text-v2-moe` — 512-token cap. **All `jina-embeddings-v3/v4/v5` and `naver/splade-v3` are non-commercial (CC-BY-NC) — disqualified regardless of quality.** `NV-Embed-v2` — non-commercial *and* gated *and* requires FlashAttention-2, so dead three ways on a T4. `Qwen3-Reranker-0.6B` scores higher than the pick but costs ~4× more and needs a yes/no-logit prompt trick (`exp(logit_yes)/(exp(logit_yes)+exp(logit_no))`, **not** a classification head) — worth an ablation at top-25, not the main path.

### Use the right benchmark for model selection

BEIR average is the wrong signal here. `mteb` 2.0.0 ships **RaR-b** (Reasoning-as-Retrieval) including an **`ARCChallenge` retrieval task** — which is literally multiple-choice science QA reframed as retrieval. Run that for model selection instead of citing BEIR averages. It is cheap, it is on-target, and "I selected my retriever on a task-matched benchmark rather than a leaderboard average" is a strong interview line. ⚠ Per-model ARCChallenge numbers were not obtainable (the leaderboard is a Gradio app); you must run it yourself.

Note also that the leaderboard has been restructured — `MTEB(eng, v2)`, MMTEB, and retrieval-only **RTEB** — and **v2 scores are not comparable to v1**, so the old "~72 MTEB average" figures you'll see quoted in 2023 writeups are legacy and must not be mixed with current numbers.

### The BRIGHT lesson, and why it is muted here

On BRIGHT (reasoning-intensive retrieval), rewriting the query into a reasoning statement roughly **doubles** retrieval quality (14.5 → 27.0 nDCG@10) — a bigger gain than swapping in a larger embedder. But your task is far more lexically anchored than BRIGHT, and crucially **your query already contains the answer text in the five options**, which is a free HyDE. So expect the gains to be muted. The transferable move is cheap and needs no LLM: **five separate retrievals, one per `question + option_i`, fused with RRF.** That is also the retrieval-side mirror of 1st place's per-option contextualization, and it is the single highest-expected-value trick on the list.

### Contextual retrieval without the API bill

Anthropic's contextual retrieval (Sept 2024) cuts top-20 failure rate **5.7% → 3.7%** with contextual embeddings, → **2.9%** adding contextual BM25, and **−67%** with reranking on top. Real gains — but it needs an LLM call *per chunk*, and you cannot contextualize millions of chunks offline. **The cheap 90% substitute is prepending the article title and section heading to every chunk before embedding** — which is exactly what the 2023 winners did, and it costs nothing. Two ablations get you the rest of the story: **Jina late chunking** (embed the long document, then pool per chunk — +9.0 nDCG on ConTEB, zero extra storage, needs an 8k-context embedder) and ⚠ `perplexity-ai/pplx-embed-context-v1-0.6b`, a model that takes chunks *grouped by document* and emits context-aware embeddings natively — contextual retrieval for free.

### Two engineering-maturity freebies

- **Use `model.encode_query()` / `model.encode_document()`** (sentence-transformers ≥5.0). They read the model's registered prompt prefixes automatically and eliminate the single most common silent-failure mode in dense retrieval. Every model has a different prefix convention (`"query: "` vs `Instruct:…\nQuery:` vs `search_query:` vs `Represent this sentence…` vs none), and getting it wrong costs 3–8 recall points with no error message.
- **int8 / binary quantization with rescoring.** Verified retention: binary alone −6.50 points, int8 alone −1.95, **binary + rescore −0.93, int8 + rescore −0.09** — ~96% retention at up to 32× memory reduction, via `sentence_transformers.quantize_embeddings()`. You don't need it at 4M vectors, but one ablation row showing you measured it reads as production thinking.

**Explicitly skip from the modern menu:** GraphRAG (no evidence it helps factoid MCQ, huge build cost), semantic chunking (repeatedly fails to justify its cost), MUVERA (community ports only), RAG-Fusion, HyDE with a local LLM (redundant given per-option retrieval), ColPali/ColQwen (visual documents), Search-R1 / R1-Searcher / ZeroSearch (these are agentic search *policies* needing a live engine — irrelevant offline), LLM listwise reranking (no API at inference, and BRIGHT shows it adds only ~3 points on top of a good query), and full multi-vector indexing (`lightonai/LateOn` has the best BEIR of anything found at 57.2/60.4 — but PLAID storage is ~36 bytes/token, so 4M chunks is **26–76 GB**; demonstrate *why it fails* on a 100k-chunk subset instead, which is a better slide than using it).

## Engineering for 9 h / 2×T4

**2×T4 is 16 GB *each*, 32 GB aggregate.** This is load-bearing: DeBERTa-v3-large fits comfortably on one T4, so the right pattern is **data-parallel sharding** (split the 4,000 rows across two processes), or better, **GPU0 runs the encoder ensemble while GPU1 concurrently runs the optional LLM leg** — near-zero marginal wall-clock for the second leg. `device_map="auto"` is for nothing in this plan. It also means 70B is impossible: 35 GB at 4-bit > 32 GB, forcing CPU offload to ~2–5 tok/s. Show that arithmetic in limitations rather than staying silent.

**Do the inference budget arithmetic before writing inference code.** DeBERTa-v3-large at 1024 tokens × 5 options × 4,000 questions ≈ 20.5M tokens forward ≈ 12 PFLOPs ≈ **~8 minutes per model on one T4**. A 5-model ensemble is ~40 min on one T4, ~20 min on two. **Conclusion: the reader is not the bottleneck — retrieval is.** Budget 1–2 h for retrieval, <1 h for the reader ensemble, and you keep 5+ hours of headroom. This is precisely why "spend it on context length and corpus diversity, not parameter count" is right *for this budget* — and why the reasoning would flip on different hardware. That nuance is what makes it sound like engineering rather than dogma.

**Offline packages.** `pip download --only-binary=:all: --platform manylinux2014_x86_64 --python-version <kaggle's> -d wheels/ ...`, upload `wheels/` as a Kaggle Dataset, then `pip install --no-index --find-links=/kaggle/input/...`. Pin against the Kaggle base image's actual torch version (print it in a scratch notebook first).

**Ship `src/` itself as a Kaggle Dataset** and have notebooks `sys.path.append('/kaggle/input/llmsci-src')`. This single-source-of-truth pattern eliminates the classic failure where notebook code and repo code silently diverge and the repo no longer reproduces the submission. Reviewers notice.

**fp16 gotcha to plan for:** DeBERTa-v3's `layer_norm_eps: 1e-7` plus fp16 on T4 is a known NaN generator. Keep LayerNorm in fp32, lower the LR, add a NaN guard that reruns the batch in fp32, set `fp16_full_eval: false`. You train locally in **bf16** (Blackwell) and on Kaggle in **fp16** (Turing has no bf16), so expect small numeric divergence — log it as a reproducibility note rather than being surprised.

**Throughput:** length-bucket the test set (sort by tokenized length, dynamic batches under a fixed token budget) for a typical 1.5–2× win over fixed padding.

**Fail-safes.** Global `TIME_BUDGET_S` with per-stage wall-clock logging and a hard assert; on exhaustion, fall back to the cheap model's predictions for unprocessed rows — never emit a partial submission. Handle Kaggle's commit/submit asymmetry (200 visible rows at commit, ~4,000 at submit): detect `len(test) == 200` and short-circuit heavy stages so commits stay fast. `tests/test_submission_format.py` asserts exact columns, ≤3 space-delimited labels from {A..E}, no intra-row duplicates, row count matches.

## Local 8 GB vs Kaggle — division of labor

**Local (RTX 5050 8 GB, 24 cores, 15 GiB RAM, ~319 GB *real* free disk — the guest reports 943 G but the WSL VHDX sits on a Windows drive with 319 G free):**
- All CPU work: chunking, sparse-retrieval experiments (270k articles is small), retrieval metrics, bootstrap CIs, difficulty matching, error analysis, plots.
- `deberta-v3-base` at 256–512 tokens — the ablation workhorse, full grids overnight. Do *all* pipeline debugging here.
- `deberta-v3-large` at 512 with LoRA or heavily-optimized full FT: feasible but tight (bf16 + grad checkpointing + 8-bit Adam + **frozen embeddings** — the 128100×1024 embedding matrix is 131M params, and freezing it saves ~1.8 GB of Adam state). ~4–7 h per run = one config per night. At 1024 it will OOM; don't fight it, move to Kaggle.
- **Hard RAM rules:** stream parquet; `datasets` with `keep_in_memory=False`; never build a global dense index locally.

**Kaggle:**
- All `deberta-v3-large` full fine-tunes at 768–1280 tokens (needs the 16 GB).
- All inference and submission.
- Retrieval over the 60–100k training questions in **CPU sessions** (12 h, don't consume GPU quota) — or skip entirely for v1 by using `cdeotte/60k-data-with-context-v2`.
- **Quota discipline:** one 1024-token large run over 60k rows ≈ 8–9 h ≈ one third of the weekly GPU quota. Ceiling of ~3 large runs per week. This is exactly why the eval harness must exist *before* the training runs — a wasted large run costs a third of a week.

## Anti-patterns

**The one that sinks the project: forking a 0.90 public notebook you cannot explain.** An interviewer needs about 90 seconds to find the bottom of that. A 0.82 you fully own beats a 0.91 you inherited, every time.

**The legitimate way to use public notebooks** — and there is one, because pretending you didn't read them would be its own red flag:
1. Read it end to end. 2. **Close the tab.** 3. Write down in prose, in your log, what it does and why. 4. Reimplement from your prose into a blank file — if you can't re-derive a line, you don't get to use it. 5. Diff your numbers against theirs and explain any gap. 6. Cite it in `CREDITS.md`: *"Took the two-stage article-then-chunk retrieval idea from jjinho's OpenBook notebook; reimplemented with `bm25s` and added RRF fusion, which they did not have."*

`CREDITS.md` converts your biggest liability into a credibility signal. Interviewers respect cited influence and punish undisclosed copying.

**Others:** reporting any number without a CI; training on the gold 200 because "more data helps" (5-fold on 200 gives folds of 40, SE ~0.05 — useless); tuning on the public LB; ensembling six embedding models before measuring one properly; loading a multi-GB dump into 15 GiB RAM; forgetting the embedder's query instruction prefix (silent −3 to −8 recall points); `truncation=True` instead of `"only_first"`; retrieving training contexts with a *better* retriever than test time; one giant notebook with no `src/` — and equally, wrapping it in FastAPI + Docker + k8s, which adds zero evidence of ML skill and eats a day; trusting `torch.cuda.is_available()` on sm_120 without running an actual kernel.
